## 0. 왜 이 작업인가 — 방향 전환의 요약

2주 반 동안 A·B·C 트랙에서 약 60개 실험을 했지만 **실제로 쓸 수 있는 밈 영상은 0개**다. 사용자와 재검토한 결과는 다음과 같다.

- 목표를 셋으로 분리했다. **목표 1(결과물): 래브라도·IG 밈을 로컬에서 완성**이 최우선이다. 목표 2(학습)와 목표 3(연구 기여)은 이번 의뢰 범위가 아니다.
- 사용자의 원래 설계는 그대로 유지한다. **imagegen으로 정체성 앵커를 만들고, SAM3로 개체를 대응시키고, 영상 모델이 시간축을 채운다.** C 트랙에서 약했던 것은 "희소 앵커 사이를 일반 FLF 모델이 상상해서 채우는" 보간 엔진이었다(C-001 개 동작 실패, C-002~C-011 약한 동작 조건의 무이득).
- 그래서 이번에는 **원본 영상 전체를 조밀한 조건으로 받는 2026년 오픈 모델**을 전파 엔진으로 쓴다. 새 모듈을 만들거나 학습하지 않는다. 지금 공개된 가장 강한 도구로 바닥선을 먼저 깔고, 실패한 축만 다음에 판다.
- 검토했지만 제외한 엔진: **Viggle-Animate / MiniMax H3**. 가중치가 MiniMax H3 Community License를 따르는데, 이 라이선스는 권리를 "Applicable Territory"(전 세계에서 EU·영국·**대한민국**·미국 제외)에서만 부여하고 그 밖의 사용·출력물 표시를 금지한다. 사용자가 한국에 있으므로 **다운로드·실행하지 않는다.**

## 1. 이번 질문

같은 원본 구간, 같은 imagegen 앵커, 같은 SAM3 마스크에서:

1. 두 오픈 전파 엔진이 **원본 두 강아지의 춤 동작을 유지하면서** 앵커의 래브라도·IG 외형을 3초 동안 이어 가는가?
2. 래브라도가 원본 개체보다 **큰 체형**으로 유지되는가, 아니면 원본 몸 구조로 되돌아가는가?
3. 두 마리를 한 번에 교체할 때 개체 뒤바뀜·합쳐짐·사라짐이 생기는가?
4. GB10에서 3초 클립 한 개를 만드는 실제 시간과 메모리는 얼마인가? 15초 전체로 확장할 수 있는 비용인가?

**최종 품질 판정은 사용자가 직접 재생해서 내린다.** Codex는 기술 판정과 자동 측정, 사용자 검토 화면까지 준비하고 품질 판정은 `HUMAN_REVIEW_PENDING`으로 둔다.

## 3. 새 Codex 세션 인수

### 3.1 환경

hostname·사용자·cwd, 저장소 root/remote/branch/HEAD/미커밋 변경, 적용되는 `AGENTS.md`, `docs/research/CHARTER.md`·`RECORDING_PROTOCOL.md`를 확인한다. 과거 세션의 shell·SSH·venv·MCP 상태를 가정하지 않는다. Spark 위에 있으면 SSH를 중첩하지 않고, 다른 호스트면 기존 `dgx-spark` 별칭과 기존 인증을 쓴다. 새 키·token을 만들거나 공개하지 않는다.

확인할 것:
- 기존 연구 Python, torch 버전(C-012 기록상 torch 2.14+cu130), ffmpeg, ComfyUI 존재 여부.
- C-001에서 쓴 **SAM3.1 Comfy integration**의 실제 위치와 호출 방식(C-001 `RESULTS.md`, `REPRODUCE.md`).
- C-001/C-004에서 쓴 **Codex native imagegen 경로**와 장부 형식(`C004_END_ANCHOR_CONSISTENCY_WORK_ORDER_KO.md` §4).
- **디스크 여유 공간.** 두 엔진의 다운로드 예상량(E1: LTX-2.3 22B distilled + IC-LoRA + 업스케일러 + Gemma 3 12B 텍스트 인코더, E2: Bernini-R + Wan2.2 T2V A14B 기반 구성요소)을 실제 저장소 페이지에서 확인하고, **여유 공간이 다운로드량의 1.3배 미만이면 해당 엔진을 `ENGINE_BLOCKED_DISK`로 남긴다.** 기존 가중치를 지워 공간을 만들지 않는다. 삭제 후보 목록만 보고에 남긴다.

### 3.2 입력 자산 — 개인 자료

공개 Git에 올리지 않는 private manifest에 역할·절대경로·SHA256을 둔다.

| 역할 | 찾는 곳 | 비고 |
|---|---|---|
| `SOURCE_VIDEO` | A 트랙 Lab/IG 프로젝트의 원본 밈 영상(1280×720·24fps·360프레임 타임라인 기준). A 트랙 기록 `output/native-quality-20261020/`, `production-plan/PRODUCTION_PLAN_KO.md` 등 | B-008의 `driver-24fps.mp4`가 같은 원본의 일부인지도 대조 |
| `CASTING` | A 트랙 M0–M2에서 고정한 배역 정의(원본의 어느 개가 Lab, 어느 개가 IG) | **A 트랙 감사에서 배역 오류가 있었다.** 고정된 최신 정의를 쓰고, 뷰어에 원본 프레임 위 라벨로 표시 |

## 4. 실행 전 고정

환경 인수 후, **다운로드·imagegen·생성 전에** 의뢰서·`PLAN.md`·동봉 설정·입력 역할(hash)·게이트·평가 기준을 commit한다. push가 안 되면 local commit 시각을 기록한다. 사후 작성을 사전 계획이라고 쓰지 않는다.

### 4.1 원본 구간 — 73프레임(3.0초)

- 프레임 수 **73** = 24fps 기준 3.0초. Wan 계열의 `4n+1`과 LTX의 `8n+1` 조건을 모두 만족한다.
- **기본 구간: 원본 타임라인 `[96, 169)`** (4.00–7.04초). A 트랙 윙크 이벤트 `[113,144)`를 포함한다.
- 사용 조건: 구간 73프레임 모두에서 SAM3가 두 개체를 각각 검출해야 한다(프레임별 개체 2개, 각 마스크 면적 ≥ 화면의 0.5%). 가림으로 일부 프레임이 빠지면 **최소 66/73 프레임** 충족을 요구한다.
- 미충족 시 **대체 구간 `[240, 313)`** (10.00–13.04초, 발차기 `[250,288)` 포함)로 한 번만 바꾼다. 둘 다 미충족이면 `SEGMENT_NOT_ESTABLISHED`로 멈추고 보고한다. 다른 구간을 탐색하지 않는다.
- 생성 시간 사전 측정(§6.3)에서 상한을 넘으면 같은 시작점의 **49프레임(2.0초)**으로 줄인다. 이 축소 규칙만 허용한다.

### 4.2 해상도 규약

- 모델 입력: **832×480**. 원본 1280×720을 높이 480으로 비율 유지 리사이즈(853×480)한 뒤 가로 중앙 832로 크롭한다. 원본·앵커·마스크에 같은 규약을 적용한다.
- 출력 fps: 24. 엔진이 다른 fps만 지원하면 실제 값을 기록하고, 뷰어에서 원본과 시간축을 맞춰 표시한다.

### 4.3 seed

두 엔진 모두 `20261103`, `20261104`. 같은 seed라도 엔진 간 noise는 다르다. 엔진 간 비교는 같은 입력에서의 결과 비교이지 같은 noise의 인과 비교가 아니다.

### 5.3 자동 수용 게이트 — imagegen 호출 전에 고정

imagegen 원출력을 수정 없이 보존하고, §4.2 규약으로 832×480 앵커를 만든다. 원본 프레임과 앵커에 SAM3(`"dog"` 텍스트 프롬프트)를 적용해 다음을 계산한다. A 트랙의 축척·정합 검사 코드가 재사용 가능하면 그것을 쓰고 출처를 기록한다.

| 게이트 | 기준 |
|---|---|
| G1 개체 수 | 앵커에서 개 정확히 2마리 |
| G2 위치 | 캐스팅별 마스크 중심 이동 ≤ 화면 가로의 8% |
| G3 Lab 크기 | Lab bbox 높이 / 원본 해당 개체 bbox 높이 ∈ [0.85, 1.60] |
| G4 IG 크기 | IG bbox 높이 / 원본 해당 개체 bbox 높이 ∈ [0.70, 1.30] |
| G5 배경 | 두 개체 마스크 합집합을 24px 팽창한 영역 바깥의 원본 대비 평균 절대 차 ≤ 12 (0–255) |

- 모두 통과하면 그 앵커를 쓴다.
- 하나라도 실패하면 **보정 호출 1회**만 허용한다. 같은 입력·같은 템플릿에 실패 항목에 해당하는 사전 문장 하나만 덧붙인다(예: G3 실패 → "래브라도의 크기를 첫 번째 이미지의 해당 강아지와 비슷하거나 조금 더 크게"). 문장 목록은 `V001_PREDECLARED_CONFIG.json`에 있다.
- 두 번째도 실패하면 **실패 항목을 기록하고, 두 번째 앵커로 진행한다.** 게이트는 품질 보증이 아니라 기록용이며, 이번 목적은 전파 엔진의 바닥선 확인이다. 단 G1(개체 수) 실패는 진행하지 않고 `ANCHOR_UNUSABLE`로 멈춘다.
- 실제 imagegen 호출 수·후보 수·모델 식별자·청구 정보(노출되면)를 장부에 기록한다. 노출되지 않으면 UNKNOWN.

### 6.1 E1 — LTX-2.3 + Union Control IC-LoRA (먼저 실행)

- 라이선스: LTX-2 Community License(연매출 1천만 달러 미만 무료, 영토 제한 없음). 텍스트 인코더 Gemma 3 12B는 Gemma Terms of Use. 실제 LICENSE 파일을 내려받아 `LICENSES.json`에 버전·날짜를 기록한다.
- 구성: `Lightricks/LTX-2.3` 공식 저장소의 `ltx_pipelines` IC-LoRA 파이프라인(또는 공식 ComfyUI-LTXVideo 워크플로). **distilled checkpoint**, `ltx-2.3-22b-ic-lora-union-control-ref0.5`, 공식 spatial upscaler(필요 시).
- 조건:
  - 첫 프레임 = §5 앵커(832×480). 이미지-투-비디오 조건.
  - 구조 조건 = 원본 구간의 **depth**(공식 문서 기본값인 Video Depth Anything). Pose(DWPose)는 사람 골격이라 쓰지 않는다. Canny는 이번에 쓰지 않는다.
  - IC-LoRA 강도 1.0, 그 밖의 설정은 공식 기본값. 실제 값을 기록한다.
- 프롬프트(영문 고정): `Two dogs dancing in the same room: a large black Labrador Retriever and a slender grey Italian Greyhound. Keep their identities, body sizes and the original background. Stable camera.`
- 주의: depth는 원본 개체의 실루엣을 담는다. 래브라도가 원본 체형으로 줄어드는지가 핵심 관측 항목이다(§1 질문 2).

### 6.2 E2 — Bernini-R, RV2V

- 라이선스: Apache 2.0(ByteDance, 2026-06). Wan2.2 기반 구성요소도 Apache 2.0. 실제 LICENSE를 기록한다.
- 구성: `bytedance/Bernini` 공식 코드와 `ByteDance/Bernini-R-Diffusers`(또는 공식 문서상 단일 GPU 경로 `infer_single_gpu.py`). `assets/testcases/rv2v/*.json`의 실제 case 형식을 읽고 같은 형식으로 case를 만든다.
- 조건:
  - 원본 영상 = §4.1 구간(832×480).
  - 참조 이미지 = §5 앵커. 공식 형식이 참조 여러 장을 허용하면 래브라도·IG 원본 사진을 추가 참조로 넣을 수 있다. 실제 사용 형식을 기록한다.
  - 지시문(영문 고정): `Replace the two dogs in the video with the two dogs in the reference image: the large black Labrador Retriever and the slender grey Italian Greyhound, matching their positions. Keep the dance motion, timing, background, lighting and camera exactly.`
- 플래너/prompt enhancer: 공식 코드가 외부 OpenAI 호환 VLM API(`BERNINI_PE_*`)를 요구하면 **외부 API를 쓰지 않는다.** 플래너 없이 실행 가능한 경로가 있으면 그것을 쓰고, 이미 Spark에서 돌고 있는 로컬 VLM endpoint가 있으면 사용자 승인 없이 새로 띄우지 않는다. 플래너가 필수인데 로컬 대안이 없으면 `ENGINE_BLOCKED_PLANNER`로 남긴다.
- 주의: 공식 환경은 H100·CUDA 12.4·torch 2.5.1로 고정돼 있다. GB10(ARM64)에서는 기존 torch 2.14+cu130을 공유하는 **격리 venv**를 만들고, pip가 다른 torch를 설치하지 않도록 `--no-deps` 등으로 막는다(C-012에서 torch 2.15가 끼어든 사고 참고). 버전 차이와 패치는 `RUNTIME_DIFF`로 남긴다.

### 6.3 시간·메모리 사전 측정

각 엔진의 첫 실행 전에 **1 denoising step만 실행하는 시간 측정**을 1회 허용한다(영상 출력으로 세지 않음). 전체 step 수로 외삽한 예상 시간이:
- E1 > 60분, 또는 E2 > 120분이면 → 해당 엔진은 49프레임(§4.1 축소 규칙)으로 바꾸고 기록한다.
- 49프레임에서도 각 상한의 1.5배를 넘으면 → 그 엔진은 `ENGINE_TOO_SLOW`로 남기고 실행하지 않는다.

### 6.4 실행 순서와 예산

| 단계 | 승인량 |
|---|---:|
| 엔진 설치·다운로드 | 엔진당 상한 90분, 실패 시 해당 엔진만 BLOCKED |
| imagegen | 최대 2회(§5.3) |
| SAM3 | 원본 구간 1회, 앵커 최대 2회, 출력 4개 각 1회 |
| 시간 측정 | 엔진당 1회 |
| 영상 생성 | E1 × 2 seed, E2 × 2 seed = **최대 4개** |
| 품질 재시도 | 0회 |
| 전체 작업 상한 | 8시간(마지막 30분은 기록·전달) |

순서: 인수 → 사전 commit → 구간 확인(SAM3) → 앵커(imagegen) → **E1 설치·측정·2회 생성** → E2 설치·측정·2회 생성 → 측정·뷰어 → 기록·전달.
E1이 막혀도 E2를 진행하고, 반대도 같다. 설치·경로·포장 같은 기계적 오류는 같은 입력·설정으로 고쳐 다시 시도할 수 있다. 결과를 본 뒤 설정을 바꾸는 재시도는 하지 않는다.

## 7. 운영 정책 — V-001 한정

과거 실험에서 미세한 swap·PSI 신호로 중단된 세션이 많았다(B-034, C-003, C-005, C-013). 사용자와의 재검토에 따라 **이번 V-001에 한해** 다음 정책을 승인한다. 기존 공통 가드 코드를 수정하지 않고, V-001 실행 사본에만 적용하며 diff를 기록한다.

- **경고만 남기고 계속:** 시작 시 기존 swap 점유량, 1GiB 미만의 swap-out 증가, PSI full avg10이 30초 미만으로 10%를 넘는 일시 상승(모델 적재 중 포함).
- **중단:** OOM 또는 OOM killer 개입, MemAvailable < 12GiB가 30초 이상 지속, PSI full avg10 > 25%가 60초 이상 지속, 보호 대상 외부 서비스(예: 8190 큐)와의 실제 충돌, 다른 사용자 GPU 작업 발견.
- 중단 시 같은 단계를 자동 재시도하지 않는다. 원인 관측을 기록하고 다음 엔진으로 넘어간다.
- 모델 작업과 환경 import 시험을 병렬로 하지 않는다. `swapoff`·재부팅·타 프로세스 종료를 하지 않는다.
