## 0. 무엇을 배웠고 왜 이렇게 바꾸나

사용자가 결과를 직접 봤고, Claude가 원본·M1·V-001 E1을 같은 시점으로 나란히 비교했다.

- **원본**: 작은 두 개가 **뒷발로 서서 사람처럼 춤춘다**(발차기, 앞발 들기). 영상 모델의 상식("개는 네 발로 선다")과 반대되는 장면이다.
- **V-002 M1(VACE 1.3B, 실루엣 마스크)**: 두 개가 처음부터 끝까지 **네 발로 서 있다.** 춤이 사라졌다. 사용자 판정은 "심각할 정도로 구리다, E1보다 나쁘다."
  - 원인 1: 뒷발로 선 개의 팽창 실루엣과 정면을 본 네 발 개의 실루엣이 둘 다 세로로 긴 덩어리라 구분되지 않는다.
  - 원인 2: 마스크 안이 회색이라 모델이 자기 상식(네 발)으로 채웠다.
  - 원인 3: 한 장의 마스크에 편집 영역과 동작 신호를 같이 맡겨 체형·털이 원본 윤곽에 갇혔다.
- **V-001 E1(LTX, 첫 프레임 앵커 + depth)**: 동작 순서는 다르지만 **뒷발로 서서 춤추는 형태는 유지했다.** 첫 프레임 앵커가 직립 자세를 전달했기 때문이다.

**결론: 이 작업에서 자세를 실제로 전달하는 것은 실루엣이 아니라 imagegen 앵커다.** 그래서 앵커를 첫 프레임 하나가 아니라 **0.5초 간격으로 촘촘히** 두고, 앵커 사이는 **원본 윤곽(canny)**으로 묶는다. 이 영상은 배경이 거의 흰색이라 canny가 다리 하나하나의 윤곽을 깨끗하게 잡는다.

**목표는 품질이다. 비교 기준은 사용자가 만든 Kling 결과다.** 속도는 기록만 하고 판단 기준으로 쓰지 않는다.

## 3. 운영

1. **펌웨어**: 2026-11-05에 사용자가 EC `0x0300050b`, SoC `0x02009b0e`로 업데이트했다. 이전 세 번의 Spark 정지는 "부하 중 로그 없는 강제 전원 차단"으로 알려진 GB10 증상과 일치했다. 시작 시 `fwupdmgr get-devices`로 버전을 기록한다.
2. **하드웨어 기록**: `~/hwlog/hw.csv`(5초 간격 GPU 온도·전력·클럭, 열 센서 전체, 가용 메모리)가 돌고 있는지 확인한다. 없으면 같은 형식으로 켜고 `free`는 `LC_ALL=C`로 실행한다. 생성마다 시작·끝 시각을 기록해 hw.csv와 맞출 수 있게 한다.
3. **실행 관리는 Spark 안에서**: 생성·측정·패키징은 Spark의 tmux 또는 사용자 systemd unit으로 실행한다. Mac 연결이 끊겨도 Spark 쪽 작업이 끝까지 진행되게 하고, 결과는 Spark에서 먼저 완성한 뒤 Mac으로 가져온다.
4. **메모리**: 모든 heavy 적재 직전 `sudo -n /usr/local/sbin/drop-caches`, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, 커널 로그 `NV_ERR_NO_MEMORY` 감시(첫 발생 시 중단), V-001 §7 중단 조건을 그대로 쓴다.
5. **외부 GPU 작업**: V-002 r1 §3.2와 같다. 3분 연속 부재 시 시작하고, 단계당 최대 120분 기다린다. 다른 프로세스를 종료하지 않는다.
6. **전원 차단이 다시 나면**: 재부팅 후 `tail -40 ~/hwlog/hw.csv`와 직전 부팅 로그를 기록하고, 남은 생성은 **멈춘다.** GPU 클럭 상한은 사용자 승인 사항이므로 Codex가 스스로 걸지 않는다.

## 4. 키프레임 앵커 (imagegen)

### 4.1 위치

원본 구간 기준 프레임 **0, 12, 24, 36, 48, 60, 72**(0.5초 간격, 7장). 원본 타임라인으로는 240, 252, …, 312다.

사전 관측: 원본의 발차기(구간 프레임 약 24 전후)와 앞발 들기(약 60~72)가 키프레임에 포함되는지 원본 9시점 시트로 확인한다. 큰 동작의 정점이 두 키프레임 사이에 걸쳐 빠지면, **그 정점 프레임 하나를 가장 가까운 키프레임과 바꿔** 7장을 유지한다. 바꾼 경우 PLAN에 근거 프레임과 함께 기록한다. 이 조정은 원본만 보고 imagegen 전에 한 번만 한다.

### 4.2 생성 순서와 입력

키프레임 0부터 순서대로 만든다. 입력 이미지는 다음과 같다.

| 순서 | 입력 | 역할 |
|---|---|---|
| Image 1 | 원본의 해당 키프레임 | 그 순간의 자세·위치·카메라·배경·반사 |
| Image 2 | 래브라도 원본 사진 | 외형 |
| Image 3 | IG 원본 사진 | 외형 |
| Image 4 (키프레임 0 제외) | **수용된 키프레임 0 앵커** | 영상 전체의 외형 일관성 기준 |

V-001 앵커(키프레임 0과 같은 원본 프레임 240)가 이미 G1–G5를 통과했다. **키프레임 0은 V-001 앵커를 재사용한다**(imagegen 0회). 나머지 6장만 새로 만든다.

### 4.3 프롬프트 템플릿

V-001 §5.2 템플릿에 아래를 추가한다. `[자세 묘사]`는 원본 키프레임을 보고 관측한 것만 채운다.

바닥에 비친 두 강아지의 반사도 새 강아지의 털색과 체형에 맞게, 위치와 모양은 첫 번째 이미지와 같게 해 주세요.

### 4.4 앵커 게이트 (imagegen 전에 고정)

V-001 G1–G5(반사 제외 실제 개 2마리, 위치, 크기비, 배경 MAE)에 다음 두 개를 더한다.

| 게이트 | 기준 |
|---|---|
| **G6 직립 자세** | 캐스팅별 bbox 세로/가로 비가 원본 같은 개체의 0.8~1.25배. 네 발로 선 개로 바뀌는 실패를 잡는다 |
| **G7 외형 일관성(참고)** | 개체별 crop의 이미지 임베딩 코사인 유사도(키프레임 0 앵커 대비). Spark에 이미 있는 임베딩 모델(예: HF 캐시의 `google/siglip2-so400m-patch14-384`)을 쓴다. **기록만 하고 탈락 기준으로 쓰지 않는다** |

- 게이트에 하나라도 실패하면 그 키프레임에 한해 **보정 호출 1회**를 허용한다. 실패 항목에 해당하는 사전 문장 하나만 덧붙인다(`V003_SCENE_CONFIG.json`의 `repair_sentences`).
- 두 번째도 실패하면 실패 항목을 기록하고 두 번째 앵커를 쓴다. 단 G1(개 수) 또는 G6(직립) 실패는 그 키프레임을 **빼고** 진행한다. 남은 키프레임이 4장 미만이면 생성하지 않고 `ANCHORS_INSUFFICIENT`로 멈춘다.
- 원출력·리사이즈본·게이트 수치·호출 장부를 모두 보존한다.

### 4.5 해상도

## 5. 영상 생성 — LTX-2.3 IC-LoRA 파이프라인

V-001 E1과 같은 고정 코드(`Lightricks/LTX-2` `e98f6d9`), 같은 가중치(distilled two-stage, Union Control IC-LoRA ref0.5, Gemma), 같은 해상도(1152×640, 73프레임, 24fps)를 쓴다. 이 버전의 CLI는 `--image PATH FRAME_IDX STRENGTH [auto|replace|guide]`로 여러 키프레임을 받는다. 실제 동작은 코드로 확인하고 기록한다.

- `guide`: 아무 픽셀 프레임에나 키프레임을 추가한다.
- `replace`: 인과적 latent 시작 프레임(0 또는 `1 + 8k`: 1, 9, 17, …, 65)에 고정한다.
- 프레임 0은 `auto`(=replace)다.

| ID | 키프레임 | 구조 조건 | 목적 |
|---|---|---|---|
| **K1** | 7장, 프레임 0은 auto, 나머지는 `guide` 강도 1.0 | **canny** IC-LoRA 1.0 | 본 후보 |
| **K2** | K1과 같음 | **없음**(IC-LoRA 끔) | 키프레임만으로 충분한지 |
| **K3** | 0·17·33·49·65 다섯 위치에 `replace` 강도 1.0. 이 위치의 앵커는 §4에서 만든 앵커 중 시간상 가장 가까운 것을 쓰고, 그 원본 프레임과의 차이(프레임 수)를 기록한다 | canny IC-LoRA 1.0 | latent 고정이 더 강한지 |

- canny 조건은 V-002 첫 실행에서 만든 1152×640 canny 영상을 hash로 확인해 재사용한다(CannyEdgePreprocessor 92/200).
- 프롬프트(영문 고정): `Two dogs dancing upright on their hind legs on a reflective white floor: on the right, a large black Labrador Retriever with a broad chest and thick legs; on the left, a slender grey Italian Greyhound. They kick and raise their front paws like dancers. Their floor reflections match them. Static camera, bright white studio.`
- seed `20261103`, `20261104`. 그 밖의 설정은 V-001 E1과 같다.
- 공식 경로가 IC-LoRA를 쓰지 않는 K2를 지원하지 않으면, 같은 two-stage 경로에서 IC-LoRA만 빼는 공식 방법을 쓴다. 그 방법이 없으면 K2는 `NOT_SUPPORTED`로 남긴다.
- 기계적 오류(경로, 형식, 프레임·해상도 배수, `replace` 위치 제약)는 V-001 개정 4의 사전 허용 규칙대로 고치고 기록한다.

### 5.1 원본 배경 후합성 (파생본, CPU)

생성 영상마다 후합성본을 하나씩 만든다(생성 영상을 대체하지 않는 별도 파생본).
- 편집 영역 = (원본 SAM 개체·반사 마스크) ∪ (출력 SAM 개체·반사 마스크)를 프레임별로 합치고, 개체 bbox 높이의 15%만큼 팽창한다. 출력 개체가 원본보다 커도 잘리지 않게 하기 위해서다.
- 편집 영역 밖은 원본 픽셀, 안은 생성 픽셀이다. 경계는 8px feather로 섞는다.
- 실패를 감추지 않도록 RAW와 POST를 항상 나란히 보여 준다.

## 6. 측정과 검토

### 6.1 자동 측정 (참고값)

| 지표 | 정의 |

| 직립 유지 | 캐스팅별 bbox 세로/가로 비의 원본 대비 비율. 프레임별, 그리고 0.8~1.25 범위 안인 프레임 비율 |

| 개체 수·뒤바뀜 | 반사 제외 실제 개 2마리 비율, 캐스팅 반대 대응 프레임 수 |

| 배경 깜빡임 | 편집 영역 밖 연속 프레임 차이의 원본 대비 비율(RAW와 POST 각각) |
| 비용 | 생성 시간, 최대 메모리, 해당 시간대의 hw.csv 최고 GPU 전력·온도·열 센서 값 |

## 7. 예산과 순서

| 단계 | 승인량 |
|---|---:|
| imagegen | 6장 신규 + 보정 최대 6회 = 최대 12회(키프레임 0은 V-001 재사용). 상한 14회 |
| SAM | 원본은 재사용. 앵커 최대 12장, 출력 6개 |
| LTX 생성 | 최대 6회(K1·K2·K3 × seed 2) |
| 품질 재시도 | 0회 |
| 전체 상한 | 5시간(외부 GPU 대기 제외). 마지막 30분은 기록·전달 |

순서: 인수 → 사전 commit(설정·게이트·키프레임 위치) → 원본 정점 관측(§4.1) → 앵커 6장(순차, 게이트) → 앵커 시트 **중간 전달** → K1 s1 → K2 s1 → K3 s1 → **중간 전달(seed 1개씩)** → seed 2 세 개 → 후합성 → 측정 → 뷰어 → 전달.

seed 1 세 개가 끝나면 seed 2를 돌리기 전에 검토 페이지와 compact ZIP을 먼저 갱신해 전달한다.
